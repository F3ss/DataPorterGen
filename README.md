# DataPorterGen

Готовое к промышленной эксплуатации CLI-приложение на Java 21 для переноса и генерации данных. Сейчас DataPorterGen поддерживает копирование базы данных MongoDB между независимыми кластерами — при необходимости с другим именем базы — и добавление детерминированно сгенерированных данных на основе исходных шаблонов в raw BSON. Приложение использует официальный синхронный драйвер MongoDB для Java; документы никогда не преобразуются через JSON.

## Возможности

- Обычные и пустые коллекции, сохранение значений `_id`, типов raw BSON и порядка полей.
- Параметры коллекций, возвращаемые `listCollections`: валидаторы, режимы валидации, параметры capped-коллекций, collation, time-series, кластеризованные индексы и pre/post images, если целевой сервер их поддерживает.
- Пользовательские индексы создаются после загрузки всех документов; `_id_` намеренно исключён. Поэтому во время стадии `COPY_DOCUMENTS` в новой целевой коллекции ожидается только автоматический индекс `_id_`. Документы индексов сохраняют ключи, имена и поддерживаемые обоими серверами параметры unique/TTL/sparse/partial/text/hashed/wildcard/hidden/collation.
- Представления (views) создаются после коллекций и зависимых представлений; поддерживаются обнаружение циклов, `viewOn`, pipeline и другие параметры представления.
- Стратегии `FAIL_IF_EXISTS` (по умолчанию), `DROP_AND_RECREATE` и недеструктивная `MERGE` «источник побеждает»: документы целевой базы с совпадающим `_id` перезаписываются пакетными unordered bulk replace/upsert-операциями.
- Выбор по точным именам через `include-collections` / `exclude-collections` с зависимыми представлениями, отфильтрованными индексами и отражением пропущенных объектов как `SKIPPED`.
- Потоковые курсоры, ограниченные пакеты документов, фиксированный параллелизм по коллекциям, ограниченная очередь исполнителя, периодические логи скорости/прогресса и корректная отмена.
- Ограниченные экспоненциальные повторы для классифицированных временных ошибок подключения и чтения. Пакетные записи используют семантику retryable writes драйвера MongoDB и не воспроизводятся вслепую, если результат мог быть частичным.
- Проверка `METADATA_AND_COUNTS` и `FULL`. Полная проверка потоково читает обе стороны в порядке `_id` и сравнивает raw BSON; для `MERGE` сверка выполняется пакетными запросами по `_id`.
- Структурированный JSON-отчёт без раскрытия секретов и стабильные коды завершения процесса.
- Отдельный режим `GENERATE` со строгими правилами YAML/JSON, циклическими шаблонами raw BSON, детерминированными значениями на основе seed, ссылками между коллекциями, предварительной проверкой уникальных индексов целевой БД и анализом без записи.
- Модульные тесты, Testcontainers-тесты с Docker, многостадийный образ и независимо проверяемые Compose-сценарии.

## Архитектура

Один модуль использует вертикальные функциональные срезы с гексагональными границами без лишней модульной обвязки:

```text
bootstrap / конфигурация                    адаптеры MongoDB / JSON / логирования
             |                                             |
             v                                             v
 migration.application <--> migration.ports.out <--> migration.domain
 generation.application <-> generation.ports.out <-> generation.domain
             \________________ shared.* __________________/
```

`migration` содержит модели, оркестрацию и исходящие порты переноса; `generation` независимо группирует DSL, проверку, генерацию и её исходящие порты. `shared` ограничен действительно общими статусами операций, endpoints, отменой, безопасными ошибками и BSON-контрактом текущих MongoDB-срезов. Классы MongoDB Driver остаются в `adapters.mongo`; Spring ограничен конфигурацией, bootstrap и CLI-связыванием. Domain-пакеты не зависят от Spring, MongoDB Driver, Jackson, логирования или файловой системы.

Порядок стадий миграции стабилен:

```text
проверка конфигурации → подключение/проверка источника → инспекция источника
→ выбор плана миграции → подключение/проверка целевой БД
→ проверка/подготовка целевой БД → создание коллекций → копирование документов
→ создание индексов → создание views → проверка результата → запись отчёта
```

Проба записи (создание, вставка и удаление технической probe-коллекции) выполняется на стадии подготовки цели — после проверки пустоты для `FAIL_IF_EXISTS`, после read-only preflight для `MERGE` и непосредственно перед удалением базы для `DROP_AND_RECREATE`; до пробы цель не мутируется.

Генерация использует отдельный конвейер и не создаёт, не удаляет и не изменяет коллекции, индексы, метаданные или представления:

```text
проверка конфигурации → инспекция источника → проверка упорядоченных зависимостей
→ snapshot ограниченных префиксов шаблонов с необязательным per-collection query → инспекция целевых коллекций и уникальных индексов
→ разрешение ID/правил → необязательная проба записи → добавление → отчёт
```

Границей документа для MongoDB служит BSON-специфичный `shared.bson.BsonPayload` — непрозрачный массив байтов. Это обеспечивает точность BSON и не раскрывает `MongoClient`, `Document` или `Bson` за пределами MongoDB-адаптера. Generation-конфиг может задавать необязательный MongoDB `find`-фильтр `query` для template snapshot каждой коллекции; без него читаются все документы. Универсальный database/payload SPI намеренно не вводится: будущие адаптеры PostgreSQL и других СУБД получат собственные payload- и metadata-модели по фактическим требованиям переноса между одинаковыми СУБД.

## Требования и сборка

- Java 21. Байткод явно компилируется с `--release 21`; более новая Java не требуется.
- Docker с Compose v2 для интеграционных/E2E-проверок.
- Доступ к настроенным Gradle/Maven-репозиториям при первой сборке либо эквивалентные внутренние зеркала/кэши.

Linux/macOS:

```bash
./gradlew clean test build
```

Windows:

```bat
gradlew.bat clean test build
```

Только быстрые unit-тесты:

```bash
./gradlew test
```

Интеграционные тесты с реальной MongoDB в двух изолированных контейнерах:

```bash
./gradlew integrationTest
```

Интеграционные тесты помечены тегом `integration`; обычная задача `test` их исключает. `build` включает `integrationTest` через `check`. Если Docker-среда не обнаружена, JUnit помечает Testcontainers-тесты как пропущенные, а не выдаёт их за выполненные unit-тесты.

## Конфигурация и запуск

Секреты следует передавать через переменные окружения, а не через аргументы командной строки: командная строка может быть видна другим пользователям операционной системы.

```bash
export SOURCE_MONGODB_URI='mongodb://source-user:source-password@source-host:27017/?authSource=admin'
export SOURCE_DATABASE='customer-service'
export TARGET_MONGODB_URI='mongodb://target-user:target-password@target-host:27017/?authSource=admin'
export TARGET_DATABASE='customer-service-copy'
export TARGET_STRATEGY='FAIL_IF_EXISTS'
export VERIFICATION_LEVEL='FULL'
export INCLUDE_COLLECTIONS='customers,orders'

java -jar build/libs/DataPorterGen.jar
```

Эквивалентный пример с аргументами командной строки:

```bash
java -jar build/libs/DataPorterGen.jar \
  --migration.source.uri=mongodb://source-host:27017 \
  --migration.source.database=customer-service \
  --migration.target.uri=mongodb://target-host:27017 \
  --migration.target.database=customer-service-copy \
  --migration.existing-target-strategy=FAIL_IF_EXISTS \
  --migration.batch-size=1000 \
  --migration.parallelism=2 \
  --migration.include-collections=customers,orders \
  --migration.verification-level=FULL
```

Spring Boot также читает [application.yml](src/main/resources/application.yml). Все стандартные возможности MongoDB URI — учётные данные, `authSource`, replica set, TLS, таймауты selection/socket/connect и настройки повторов драйвера — напрямую поддерживаются официальным драйвером. Исключение: URI цели с неподтверждаемым write concern (`w=0`) отклоняется на этапе валидации конфигурации (код 2) до подключения к цели — все записи `MIGRATE`, `MERGE` и `GENERATE` требуют подтверждения записи; это же условие проверяется по фактическому результату каждой операции записи.

Краткая справка CLI доступна через `java -jar ... --help`. Некорректные или пустые точки подключения, системные базы данных, небезопасная миграция в ту же базу того же кластера, недопустимые границы и неизвестные enum-значения приводят к завершению до создания любого клиента базы данных. Принадлежность одному кластеру определяется нормализацией endpoints (нижний регистр хостов, подстановка порта `27017` по умолчанию, нечувствительность к порядку seed-списка и query-строке), а после подключения цели — дополнительно пересечением разрешённых адресов серверов топологии, что распознаёт алиасы вроде `localhost` и `127.0.0.1`, варианты `mongodb://`/`mongodb+srv://` и частично совпадающие seed-списки реплик. В обоих случаях ошибка классифицируется как конфигурационная (код 2) и происходит до любых изменений цели.

### Выбор коллекций

Два свойства выбора взаимоисключающие и принимают разделённые запятыми точные имена коллекций с учётом регистра:

```yaml
migration:
  include-collections:
    - customers
    - orders
  exclude-collections: []
```

- Оба списка пусты: мигрируются все пользовательские коллекции, индексы и views.
- Заполнен только `include-collections`: мигрируются только указанные коллекции, их индексы и views, чья цепочка `viewOn` разрешается в выбранную коллекцию.
- Заполнен только `exclude-collections`: мигрируется всё, кроме указанных коллекций, их индексов и views, для которых больше нет выбранной базовой коллекции `viewOn`.
- Заполнены оба списка: ошибка конфигурации с кодом завершения `2`; очистите одно из свойств.
- Неизвестные имена: ошибка конфигурации после инспекции источника, но до любого подключения к целевой БД или проверки записи. Имена views и системных коллекций нельзя использовать для выбора коллекций.

Пробелы, пустые элементы и дубликаты нормализуются. Исключение всех исходных коллекций допустимо и создаёт успешный пустой план, где каждый исключённый объект отмечен как `SKIPPED`. Под зависимостью view понимается `viewOn`; ссылки на коллекции внутри pipeline-операторов `$lookup` или `$unionWith` автоматически не выбираются.

### Режим генерации данных

`GENERATE` выполняет точно запрошенное количество upsert-операций в уже существующих коллекциях. Новый `_id` вставляется, существующий полностью заменяется; поэтому итоговый прирост коллекции может быть меньше `count`. По умолчанию raw-BSON шаблоны выбираются воспроизводимыми перемешанными циклами без повторов (`templateSelection: SHUFFLED_CYCLE`); прежний порядок `i % count` доступен через `SEQUENTIAL`. Именованные `sharedDates` позволяют использовать один миллисекундный `Instant` в нескольких полях и коллекциях одной итерации, выводя его как BSON Date или строки разных Java `DateTimeFormatter`-форматов. Правило `randomAlphaNumStringBetween` выбирает целое из `[min,max)`, кодирует его uppercase base-36 и дополняет нулями слева до точного `length`. `weightedChoice.choices[].value` принимает как literal shorthand, так и полноценное вложенное правило с `kind`; выбранная ветка вычисляется рекурсивно. Доказуемые `_id` принимаются как прежде. Если доказательство не сработало, explicit `_id` допускается при наличии достижимого `randomString` или `randomAlphaNumStringBetween` в любой части вложенного `concat`, через локальный `ref`, ссылку на предыдущую коллекцию или в каждой возможной ветке `weightedChoice`. Перед записью CLI и JSON-отчёт всегда показывают `POSSIBLE _id COLLISIONS` с общим random keyspace и birthday-оценкой либо `unknown`; weighted-распределение пока оценивается как `unknown`. Аварийный `allow-unproven-ids=true` разрешает другие required scalar explicit `_id`, кроме фактически статических literal-правил, но не ослабляет secondary unique-проверки. Режим никогда не создаёт и не удаляет целевые объекты и не изменяет метаданные, индексы или views. Источник и цель могут быть одной базой MongoDB: ограниченный snapshot-префикс каждой исходной коллекции завершается до инспекции цели или записи, поэтому документы текущего запуска не могут стать шаблонами.

Документы записываются упорядоченными пакетами на коллекцию: один логический блок последовательных итераций `batchSize` генерируется и записывается ordered `bulkWrite` upsert-операциями, а до `parallelism` воркеров обрабатывают разные блоки concurrently. Память материализованных результатов ограничена `maxInFlightMegabytes`: бюджет байтов поровну делится между воркерами, воркер материализует документы только в пределах своей доли, а логический блок при необходимости детерминированно делится на несколько физических write-батчей (каждый не больше доли воркера и 32 МиБ) — значения документов и порядок итераций при этом не меняются. Документ, превышающий общий лимит `maxInFlightMegabytes`, завершает генерацию ошибкой до записи (в том числе в validate-only прогоне). Порядок завершения блоков недетерминирован, но значения документов и группировка по пакетам детерминированы: они выводятся из стабильных координат `(seed, collection, iteration, path)`, а не из порядка выполнения. Проверки вторичных unique-индексов выполняются одним пакетным запросом на индекс на физический батч до его записи; окончательным арбитром уникальности остаётся MongoDB.

Длительные фазы логируют ход выполнения: чтение snapshot-префиксов (по коллекциям — количество шаблонов и байтов), предзаписная проверка правил и сама запись (итерации/документы) сообщают прогресс примерно не чаще раза в 5 секунд. Предзаписная проверка правил использует те же `batchSize`/`parallelism`: блоки итераций распределяются между воркерами, значения по-прежнему зависят только от координат, а сообщение об ошибке соответствует первой падающей итерации последовательной проверки.

Для snapshot используется 99% от `maxWorkingMegabytes` (по умолчанию 100 МБ); этот бюджет целочисленно делится на равные доли между настроенными коллекциями без перераспределения остатка. Каждый шаблон занимает точный размер raw BSON плюс 4 байта длины и 8 байт offset-индекса. Первый непомещающийся документ не сохраняется, cursor коллекции закрывается, а генерация циклически использует уже сохранённый префикс. Пустая коллекция или первый документ, не помещающийся в её долю, завершает preflight до подключения к цели. Snapshot-каталог и файлы создаются с правами только для владельца (POSIX-проверка или Windows owner-only ACL); если права подтвердить нельзя, запуск завершается до чтения документов, а неудачная очистка snapshot отражается предупреждением `CLEANUP_SNAPSHOT`. При усечении отчёт предупреждает, что анализ `_id` и validate-only coverage относятся только к сохранённому префиксу.

Подробная настройка, запуск, работа с шаблонами и примеры всех правил — включая статическую строку через `literal` — описаны в [руководстве по генерации](GENERATION.md). Готовый полный конфиг находится в [generation.example.yml](generation.example.yml).

### Стратегии для существующей целевой БД

- `FAIL_IF_EXISTS`: завершается до создания коллекций, если целевая БД содержит пользовательскую коллекцию или view.
- `DROP_AND_RECREATE`: проверяет цель, удаляет целевую базу и затем создаёт полную копию. В лог записываются безопасный URI, имя базы и деструктивная стратегия; учётные данные не записываются.
- `MERGE`: никогда не удаляет базу, коллекцию, документ, индекс или view. Выбор объектов применяется до доступа к цели, а объекты, существующие только в цели, остаются нетронутыми. Существующие выбранные коллекции должны иметь совместимые нормализованные параметры; имя выбранной коллекции, занятое view или объектом несовместимого типа, вызывает preflight-конфликт. Существующие одноимённые индексы и views должны быть эквивалентны и отражаются как сохранённые/`SKIPPED`; отсутствующие создаются после документов. Конфликтующие одноимённые индексы, эквивалентные ключи под другим именем и несовместимые views приводят к ошибке до записи документов.

Конфликты документов `MERGE` определяются точным совпадением `_id` и решаются по принципу «источник побеждает»: каждый исходный batch переносится одним пакетным unordered `bulkWrite` replace/upsert-операций — отсутствующие `_id` вставляются, а существующие целевые документы перезаписываются точным raw BSON исходного документа. В отчёте `replacedDocuments`/`conflicts` показывают число перезаписанных документов. Операции внутри batch независимы (исходные `_id` уникальны), поэтому unordered-порядок не меняет итоговое состояние при успехе, а при ошибке применяется обычная консервативная семантика «результат может быть частичным и вручную не повторяется».

Настройка `migration.merge.document-conflict-strategy` и политики `FAIL`/`KEEP_TARGET`/`REPLACE_TARGET` удалены. Если старый ключ остался в YAML, аргументах или переменной `MERGE_DOCUMENT_CONFLICT_STRATEGY`, он молча игнорируется; удалите его из конфигурации и учтите, что `MERGE` теперь всегда перезаписывает совпавшие по `_id` документы.

Перенос использует ограниченные исходные batch-пакеты и backpressure. MongoDB остаётся окончательным арбитром конкурентных гонок и уникальных индексов, существующих только в цели. Приложение не повторяет вручную неоднозначную вставку или замену. MERGE не является транзакционной, возобновляемой операцией или заменой snapshot источника. После прерванного запуска необходимо проверить отчёт и состояние цели перед повтором.

### Согласованность и проверка

`BASIC` — единственный реализованный режим согласованности. Он **не** создаёт атомарный snapshot всей базы. Записи в источник во время миграции могут привести к логически несогласованному результату; если нужна согласованная копия, остановите записи в источник. Это ограничение указывается в каждом отчёте.

`METADATA_AND_COUNTS` проверяет обязательные объекты, нормализованные параметры коллекций, определения индексов и views, а также counts. Он не заявляет идентичность документов. Для `MERGE` дополнительные целевые объекты и документы допустимы, а ожидаемый count равен целевому count на preflight плюс фактически вставленные документы; перезаписи count не изменяют. `FULL` дополнительно выполняет ограниченные raw-BSON проверки: без `MERGE` обе стороны потоково читаются в порядке `_id` и сравниваются побайтово, а для `MERGE` каждый выбранный исходный документ находится в цели одним пакетным `$in`-запросом по `_id` на batch и должен совпадать побайтово; дополнительные целевые документы допустимы, а SHA-256 fingerprint с постоянным объёмом памяти сверяется с ожидаемым состоянием переноса. Полная проверка может быть дорогой на больших базах.

### Необходимые привилегии MongoDB

Для источника нужны права `listDatabases`, `listCollections`, `listIndexes`, `find` и `count` на выбранную исходную базу. Для цели нужны `listCollections`, `listIndexes`, `find`, `count`, `createCollection`, `dropCollection` (для пробы записи), `insert`, `update`/`replace` для `MERGE`, `createIndex`, создание views и, для `DROP_AND_RECREATE`, `dropDatabase`. MERGE выполняет все read-only проверки метаданных/индексов/views до пробы записи.

## Коды завершения и отчёт

| Код | Значение |
|---:|---|
| 0 | запрошенная операция миграции/генерации завершилась успешно |
| 2 | некорректная конфигурация или startup binding |
| 3 | ошибка подключения к источнику или проверки чтения |
| 4 | ошибка подключения к цели, preflight генерации или проверки записи |
| 5 | ошибка подготовки цели или целевая БД уже существует |
| 6 | миграция метаданных/документов завершилась ошибкой или частично |
| 7 | миграция завершена, но проверка обнаружила различия |
| 8 | запрошена отмена или корректное завершение |

JSON-отчёт атомарно записывается в `migration.report-path` (для генерации по умолчанию используется `reports/generation-report.json`, если стандартный путь миграции не был переопределён). Порядок объектов в отчёте детерминирован: результаты копирования коллекций следуют порядку migration plan независимо от порядка завершения параллельных воркеров, стадии упорядочены по времени выполнения. Доступность пути отчёта проверяется пробой (создание каталога и временного файла с последующим удалением) на стадии валидации конфигурации — до подключения к источнику и цели; недоступный путь завершает запуск ошибкой конфигурации (код 2), не мутируя цель. Отчёты миграции содержат `migrationId`, стратегию цели, результаты выбора и проверки. Результаты коллекций MERGE добавляют явные поля `sourceDocuments`, `insertedDocuments`, `replacedDocuments`, `conflicts` (число перезаписанных документов) и количество обработанных BSON-байтов в `bytes`. Каждый secondary index логируется как `ordinal/total`; неудачный индекс записывается и как failed-объект, и как проблема стадии `CREATE_INDEXES`. Для серверных ошибок MongoDB диагностика включает безопасную классификацию `code`/`codeName`, но исключает исходный текст серверной ошибки, поскольку duplicate-key и validator-ошибки могут содержать значения документов. Каждая проблема отчёта несёт типизированное поле `failureKind` (`CONFIGURATION`, `SOURCE_CONNECTION`, `SOURCE_INSPECTION`, `TARGET_CONNECTION`, `TARGET_PREPARATION`, `DOCUMENT`, `METADATA`, `VERIFICATION`, `GENERATION`, `CANCELLED`, `UNKNOWN`); коды завершения вычисляются по этому полю, а не по тексту сообщения. `safeToRetry` равен true, только если не произошло постоянной операции create/drop/insert/replace/index/view над целью; preflight-конфликт безопасен для повтора, а любая неоднозначная попытка записи консервативно считается небезопасной. Отдельные отчёты генерации содержат `generationId`, разрешённый seed, `templateSelection`, флаг validate-only, SHA-256 hash конфигурации генерации, упорядоченные counts коллекций, разрешённые стратегии `_id`, `snapshotTemplates`, `snapshotBytes`, `snapshotTruncated`, количество generated-байтов, лимиты, длительности стадий и `safeToRetry`. Оба типа отчётов содержат очищенные endpoints, имена баз, временные метки, предупреждения и ошибки. Они никогда не содержат документы, сгенерированные значения, учётные данные, токены, чувствительные параметры URI или содержимое конфигурации генерации.

## Сквозные сценарии Docker Compose

### Миграция

Сценарий создаёт аутентифицированные изолированные сервисы `mongo-source` и `mongo-target` с разными volumes. Инициализация источника идемпотентна и создаёт `source_catalog` с обычными, capped и пустыми коллекциями, валидаторами, репрезентативными BSON-значениями, unique/compound/partial/hashed/sparse/TTL индексами (включая пять secondary indexes в одной коллекции) и view. Мигратор копирует её в чистую `migrated_catalog` со стратегией `FAIL_IF_EXISTS`; после успеха контейнер остаётся healthy до завершения проверки, что предотвращает гонку `--abort-on-container-exit`. Отдельный контейнер `mongosh` напрямую проверяет точные имена и определения secondary indexes и остальные факты источника/цели, возвращая ненулевой код при любом расхождении.

```bash
docker compose up --build --abort-on-container-exit --exit-code-from migration-verifier
```

Успешный запуск завершается строкой:

```text
E2E_VERIFICATION_SUCCESS source=source_catalog target=migrated_catalog objects=5
```

Полезные команды:

```bash
docker compose logs dataportergen migration-verifier
docker compose cp dataportergen:/app/reports/migration-report.json ./migration-report.json
docker compose down
docker compose down --volumes
```

`down` сохраняет volumes; `down --volumes` выполняет явный полный сброс. Поскольку сценарий намеренно проверяет `FAIL_IF_EXISTS`, повторный запуск с сохранённым volume успешно заполненной цели должен завершиться ошибкой. Используйте `down --volumes` только для осознанного создания чистой E2E fixture. Порты MongoDB на host не публикуются.

### Генерация данных

Сценарий генерации использует одну аутентифицированную базу MongoDB одновременно как источник и цель. Он сохраняет snapshot двух исходных коллекций, добавляет трёх customers и три зависимых orders и независимо проверяет циклический выбор шаблонов, явные и зависящие от цели последовательности, детерминированные ObjectId, межколлекционные ссылки, уникальные индексы, counts и сохранность исходных шаблонов.

```bash
docker compose -f compose.generation.yml config
docker compose -f compose.generation.yml up --build --abort-on-container-exit --exit-code-from generation-verifier
```

Успешный запуск завершается строкой:

```text
GENERATION_E2E_VERIFICATION_SUCCESS database=generation_catalog generatedCustomers=3 generatedOrders=3
```

Fixture использует детерминированные ID, поэтому повторяйте сценарий с чистым тестовым volume:

```bash
docker compose -f compose.generation.yml down --volumes
```

Порты MongoDB на host не публикуются. Учётные данные и данные предназначены только для локальной тестовой fixture.

### MERGE

Отдельный сценарий MERGE повторно использует исходный тестовый набор с несколькими коллекциями, включая пять вторичных индексов в `customers`. В начальном состоянии цели находятся один конфликтующий customer, по одному существующему только в цели customer, коллекции, индексу и представлению, два эквивалентных исходных индекса и эквивалентное исходное представление. Мигратор запускает `MERGE` с уровнем `FULL`; конфликтующий документ перезаписывается точным BSON источника, а независимый verifier на `mongosh` проверяет перезапись, точный BSON вставленных документов, созданные/сохранённые индексы и представления, количества документов и сохранность всех данных, существующих только в цели.

```bash
docker compose -f compose.merge.yml config
docker compose -f compose.merge.yml up --build --abort-on-container-exit --exit-code-from merge-verifier
```

Успешный запуск завершается строкой:

```text
MERGE_E2E_VERIFICATION_SUCCESS source=source_catalog target=merge_catalog objects=7 inserted=3 overwritten=1
```

Просмотр отчёта и остановка сценария без удаления volumes:

```bash
docker compose -f compose.merge.yml logs dataportergen merge-verifier
docker compose -f compose.merge.yml cp dataportergen:/app/reports/merge-report.json ./merge-report.json
docker compose -f compose.merge.yml down
```

Детерминированная fixture не предназначена для повторного запуска поверх уже объединённой цели. Используйте `down --volumes` только при явном намерении полностью сбросить fixture; приложение и Compose-сценарий никогда не удаляют volumes автоматически.

## Границы MVP и ограничения точного копирования

Приложение не мигрирует пользователей/роли MongoDB, системные базы/коллекции, sharding или состояние balancer, параметры кластера, конфигурацию аудита, сертификаты или секреты. Оно не предоставляет атомарные snapshots между базами, догоняющую синхронизацию через change stream, checkpoints/resume, throttling, filters/masking или REST/UI. MERGE не является транзакционной, не удаляет данные, существующие только в цели, и не согласует уникальные индексы, существующие только в цели, кроме выдачи безопасной классификации ошибки MongoDB. В generation v1 отсутствуют faker-библиотека, скрипты, пользовательский Java-код, арифметические выражения, ссылки на нижестоящие коллекции/предыдущие итерации, rollback, resume, создание метаданных и автоматическое удаление устаревших snapshots.

Разные версии MongoDB могут возвращать разные параметры или отклонять параметры, не поддерживаемые целевым сервером. Ошибки создания коллекций, индексов и views отражаются с контекстом объекта и стадии и завершают запуск ошибкой; они никогда не игнорируются молча. Серверные/внутренние метаданные, например UUID коллекций и автоматический индекс `_id_`, намеренно не создаются заново. Повторы записи driver подчиняются URI подключения и протоколу retryable writes сервера; приложение не воспроизводит неоднозначный batch вручную. Частичный запуск `FAIL_IF_EXISTS` или `MERGE` обычно нельзя безопасно перезапустить без проверки оператором; `DROP_AND_RECREATE` может заново построить цель, но после первого деструктивного действия также консервативно помечается как небезопасный для повтора.
